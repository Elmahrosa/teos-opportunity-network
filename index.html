A scanner that scores opportunities —
and tells you exactly why.

TEOS discovers GitHub opportunities (bounties, projects, jobs, hackathons), normalizes and deduplicates them, matches them against your profile with a fixed, weighted, deterministic score, and sends a Telegram alert only when the threshold is cleared. An LLM is optional and capped — it can never make the decision for you.

How the pipeline works

Every pass runs the same seven stages in order: collect, clean, deduplicate, match with hard rules + score, persist evidence, gate by threshold, then notify.

Discover→ Normalize→ Deduplicate→ Match→ Persist→ Threshold→ Notify
STEP 1 · COLLECTOR

Discover

Queries api.github.com/search/issues with an optional Bearer token. Credentials are never hard-coded.

STEP 2 · NORMALIZER

Clean

Deterministic normalization of title, description, URL, skills, type, budget, currency, dates. Produces a SHA-256 content_hash.

STEP 3 · DEDUP

Deduplicate

UNIQUE(source, external_id) is the hard boundary. Provenance is never destroyed — input_snapshots is append-only.

STEP 4 · MATCHER

Match

Hard rules + weighted score + multi-agent semantic signal from free OpenAI-compatible models (deterministic median fusion, neutral-50 fallback).

STEP 5/6 · REPOSITORY

Persist

Evidence is saved with its weights version. Re-saving never overwrites history — idempotent on (opportunity, user, version).

STEP 7 · GATE

Threshold

≥85 → ALERT, ≥60 → LOG, below → IGNORE. Enforced in code and by PostgreSQL CHECK constraints.

STEP 9 · DELIVERY

Notify

Telegram messages go through PENDING → SENDING → SENT / FAILED → RETRY. At most one SENT per (match, user, channel).

STEP 10 · RUNTIME

Run

--once one pass, --loop on an interval (default 300 s), or a free scheduled GitHub Actions scanner hourly. Without a token the same pass dry-runs honestly.

Opportunity types: JOB · PROJECT · BOUNTY · HACKATHON · SOFTWARE · SERVICE

Scoring that can't be gamed

The score is a fixed linear combination of component scores. Identical inputs always produce the identical score — the weights are the configuration, and they must sum to exactly 1.0 or the engine refuses to run.

HYBRID_V1 — production weights ACTIVE

// ScoringConfig.CreateHybridV1() — must total 1.0
{"skills":0.35,"experience":0.20,"budget":0.15,
 "type":0.10,"location":0.10,"urgency":0.05,
 "semantic":0.05}

Replay/benchmarks re-score only the immutable input_snapshot — the LLM is never called again, and no current state can leak in.

HYBRID_V2 — experimental EXPERIMENTAL

// Explicit opt-in only; never replaces V1 in production
{"skills":0.30,"experience":0.20,"budget":0.15,
 "type":0.10,"location":0.10,"urgency":0.05,
 "semantic":0.10}

Weights are validated (must total 1.0), versioned, and stored with every match. No unknown weights, no negatives.

Decision thresholds

ScoreDecision
≥ 85ALERT — eligible for notification
≥ 60LOG — watched, not alerted
< 60IGNORE

Recommended action

ScoreAction
≥ 90APPLY_NOW
≥ 75REVIEW
< 75PASS

Invariants are enforced in code and by DB constraints: a score ≥ 90 can never be IGNORE or PASS.

Semantic signal — free multi-agent ensemble: several free OpenAI-compatible models (Groq, OpenRouter, Gemini, Mistral, GitHub Models, local Ollama) score relevance in parallel. Valid judgments fuse by a deterministic median; a failing model is skipped, never a crash; if all fail, the engine reports the documented neutral-50. Replay reuses the stored snapshot — the models are never re-called.

The Telegram bot — @teoson_bot LIVE · VERIFIED

The bot is a notification/UI layer only — it never re-scores, matches, or calls an LLM. It reads the persisted match result and delivers it verbatim. It was verified end-to-end: a real seeded opportunity scored 90.00 → ALERT / APPLY_NOW and was delivered (provider message id 4, sent 2026-10-13 03:34:07 UTC).

Delivery guarantees

  • One delivery row per (match, user, channel) with status flow PENDING → SENDING → SENT / FAILED → RETRY.
  • Claims use FOR UPDATE SKIP LOCKED — safe for concurrent workers.
  • A partial unique index enforces at most one SENT per (match, user, channel).
  • Messages are HTML-escaped and capped below Telegram's 4096-char limit.
  • 429 responses honor retry_after; tokens are redacted from every error path.

The GitHub Action — TEOS Sovereign Repo Valuator

A composite action in its own repository — Aymanseif/teos-repo-valuation — that values a repository as an asset: a deterministic 0–100 score plus an estimated dollar range. No LLM involved. Works on any runner with .NET 8 support; the token defaults to the workflow's github.token.

Usage

# .github/workflows/valuations.yml
- uses: Aymanseif/teos-repo-valuation@v1.2.3
  with:
    github-token: ${{ github.token }}
OutputMeaning
scoreTEOS Score 0–100
valuationEstimated range
decisionALERT / LOG / IGNORE
